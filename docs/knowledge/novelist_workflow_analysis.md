## 二、 发现的业务流具体问题与隐患

### 1. 偏好记忆系统存在“单向孤岛”

- **问题描述**：在 [schema.ts](file:///e:/NextCloud/coding/netx.js/story/db/schema.ts) 中定义了 `user_preferences` 表，后端也提供了 `POST /api/preferences` 用来保存用户的题材偏好。但前端的 `HomeDashboard` 偏好展示区是**纯静态只读**的。
- **业务隐患**：用户如果想要修改自己的创作偏好，唯一的途径是通过外部抓包或 API 调试工具发起 POST 交互，页面上没有任何入口允许设置。

### 2. 问答向导中“AI 随机推荐”纯属客户端静态模拟

- **问题描述**：在 [novel-wizard.tsx](file:///e:/NextCloud/coding/netx.js/story/components/novel-wizard/novel-wizard.tsx) 中，当用户点击 Q4-Q8 的“随机生成”时，前端逻辑触发了 `buildRandomChoice`。这是一个纯客户端根据 Genre 字眼来硬编码匹配文本的静态函数。
- **业务隐患**：既然该系统以 AI 创作为核心，此时应该发挥 LLM 辅助灵感的能力。只用写死的硬编码映射，导致其提供的辅助创意极其贫瘠，违背了 Novelist 技能设计中“为用户脑补高水准设定”的初衷。虽然后台实现了 `/api/novel/[id]/wizard/suggest` 接口，但前端完全没有将其接入到这里。

### 3. 大纲确认（Phase 2）缺少“人设档案”的微调编辑能力

- **问题描述**：当前界面为用户展示了完整的角色设定档案（Character Profiles），但它是作为只读 Card 显示的。用户唯一能编辑的只有大纲表格每一章的摘要（`outlineSummary`）。
- **业务隐患**：如果在规划生成时，AI 生成的主角性格、致命缺陷或者反派配角的名字不合用户心意，用户在大纲确认阶段**无法做任何修改**，必须带着错误的人设进入第 3 阶段（疯狂创作），后续生成的所有剧情都将受此人设偏离的影响，且无法在源头上纠正。

### 5. 流式自动写作缺少“可选自动去 AI 味”润色功能

- **问题描述**：在 [generator.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/generator.ts) 自动写作循环中，直接将 LLM 生成的初稿拿去进行校验，如果过了字数与悬念检测，就直接标记为 `completed` 落库，没有提供可供用户选择开启或关闭的自动化润色（去AI味）机制。
- **业务隐患**：Novelist 技能标准强调，初稿通常有明显的“AI味”。虽然全自动润色有助于降低 AI 痕迹，但在某些情况下用户可能希望保留原汁原味的生成初稿以方便自己手动重写。因此，完全缺失这一可选开关会导致写作灵活性受限，而直接忽略该步骤又会导致全自动成稿的 AI 痕迹过重。

### 6. 上下文记忆机制过于简陋，极易造成前后文断层

- **问题描述**：
  1. 在 [generator.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/generator.ts) 中，写作后续章节时，传给下一个章节的唯一前文剧情参考是：`previousChapterSummary = content.slice(-500)`（前一章最后 500 字内容）。
  2. 自动写作过程中，并没有像 Novelist 规范那样，在写完一章后，**提炼 300-500 字的章节摘要**并将其回写更新到对应的大纲中。
- **业务隐患**：500 字的物理截断很可能会切断关键剧情的发生，且大模型无法理解章节全局走向。随着小说越写越长，由于看不到全局的章节提炼，角色性格可能会发生突变，前期埋下的悬念或线索在后文会被直接漏掉或忘却。

## 三、 针对性的优化与改造方案

为了消除上述流程隐患并使项目高度对齐 Novelist Skill v2.0，建议在后续的开发规划中加入以下技术改造：

### 1. 交互增强：偏好设置管理界面与人设可编辑化

- **修改主页偏好展现**：将 Dashboard 中的偏好卡片改造为可编辑的表单形式，或者添加“编辑偏好”对话框，直接调用 `POST /api/preferences` 更新数据库，实现个性化数据持久化。
- **在 Phase 2 提供人设修改**：在 `/novel/[id]/plan` 大纲规划确认页，除了 `OutlineCard` 之外，引入 `CharacterProfileEditor`，使用户可以在正式启动写作之前，手动修改并提交 AI 拟定的角色特征与姓名关系。

### 2. 智能化优化：引入动态 AI 随机推荐

- **对接 Suggest API**：将 [novel-wizard.tsx](file:///e:/NextCloud/coding/netx.js/story/components/novel-wizard/novel-wizard.tsx) 中的随机按钮动作改为异步请求服务端 `/api/novel/[id]/wizard/suggest?questionId=xxx`。基于已填报的核心定位，使用大模型结合上下文动态生成当前配置项的个性化创意选项。

### 3. 解析器健壮性：升级大纲生成与解析方案

- **引入 JSON / JSON Schema 或强化解析容错**：在 `generator.ts` 与大纲解析端，可以通过设定大模型生成标准 JSON 串、利用 Markdown Markdown Table Parser 库替换裸正则、或增加对于格式不符时的提示词防御与重试机制，防止由于单字符多余破坏整本小说的章节初始化。

### 4. 写作算法迭代：集成可选的自动润色流与全局摘要生成

- **引入可选的自动化 Polish 环**：在写作启动配置或用户偏好中增加“是否自动润色正文”开关。在 [generator.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/generator.ts) 生成正文后，若该开关开启且初稿生成成功，应当在进入 Validator 校验之前，调用一次 `polishSelectedText` 润色通道对全章文本进行快速降 AI 味自动润色。若开关关闭，则直接跳过润色环节进行校验，以给予用户最大的创作灵活性。
- **智能摘要与滚动大纲更新**：每章写作成功且通过校验后，后台应自动调用 LLM 生成 300 字摘要，并更新到 `chapters` 数据库的 `outlineSummary`（或回填至主 outline 段落），为下一章的写作构建真正结构化的“前情提要”大纲链路。

## 四、 上下文一致性保障分析

在长篇小说创作中，无论是否发生多视角切换，如何保证故事线索连贯、人设不崩、时间线无硬伤，都是核心痛点。以下结合 `chinese-novelist` 标准规范，分析如何在本项目实际代码库中实现高质量的上下文一致性保障。

### 1. 一致性保障的“标杆设计”

依据 Novelist 规范，系统采用**“通用框架打底，细节区别处理”**的上下文保证框架：

#### A. 通用的上下文保障底层（非多视角的核心支柱）

底层的动态工作流是通用的，不论小说是否切换视角，均通过以下手段锁定故事链路：

- **信息底座锁死**：利用静态的“人物档案”（对应本项目的 `novelProfiles`）与“大纲规划”（对应 `chapters.outlineSummary` 的初始化内容）锚定人设和章节主权。
- **写前分析感知**：在新章节动笔前，Agent 必须读取所有已完成章节摘要、上一章落点以及关键出场角色的动态状态（位置、情绪、已知信息、人际关系关系）。
- **写后闭环反哺（滚动摘要）**：每章生成并校验通过后，自动总结 300-500 字的章节摘要更新大纲。这是应对长文本遗忘的最核心通用机制——大模型借助“不断延伸的摘要链”掌握前情提要，而非粗暴截取原文片段。

#### B. 叙事视角下的“区别处理”（Prompt 指令约束差异）

针对不同的叙事视角（POV 选项），系统在构建写作 Prompt 时进行精细的区别化控制：

- **第一人称视角（主角自述，“我”）**：强化语言风格的主观情绪（偏见、内心活动）强一致性；严格限制认知盲区——“我”决不能获取视角外的信息，除非通过互动感知。
- **第三人称限制视角**：叙事虽用“他/她”，但信息边界依然等同于主角的视点范围。不能描写视角人不在场的任何画面或未公开信息。
- **第三人称全知视角（上帝视角）**：取消认知盲区限制，但重点约束 AI 保持场景/视点过渡的平滑性，防止在多个角色念头之间生硬、高频切换（防止 Whiplash 现象），同时注重多线索时序的宏观连贯性。
- **多视角切换（Multi-POV）**：重点在于多视点间的**“信息隔离与拼图拼接”**，利用不同角色认知形成的“信息差”制造剧情张力和悬念，同时防范视角转换时的时空倒错。

### 2. 结合本项目实际的 Gap 与改造方案

当前项目的底层结构（[generator.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/generator.ts)、[chapter-prompt.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/chapter-prompt.ts)、`schema.ts` 等）已初具一致性链路的雏形，但在长文本连贯性以及多视角控制上仍存在明显的缺陷：

#### 🔴 Gap 1：出场人物档案“无脑全量加载”，导致 LLM 视角混淆

- **实际现状**：在 [generator.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/generator.ts#L49) 中，系统加载了该小说对应的全部 `characterProfiles` 传入 prompt，没有任何筛选。
- **视角隐患**：随着章节推进和视角切换，出场人物可能非常多。将所有人物档案塞进上下文，不仅浪费 Token，更容易导致 LLM 在撰写当前 POV 章节时，将未出场角色的口头禅、性格特征或人际关系张冠李戴。
- **改造方案**：
  1. 优化大纲设计，在生成大纲时确定每章的 `activePOV`（视角主人，即使是单主角视角也需锚定）和 `castList`（当前章节的出场人物名单）。
  2. 在 [generator.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/generator.ts) 中加载 `characterProfiles` 后，依据当前章节的 `castList` 进行**精准过滤**，仅将当前视角角色及本章互动的角色 Profile 喂给 [chapter-prompt.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/chapter-prompt.ts#L80-L87)，从而在物理上隔离无关角色的噪声干扰。

#### 🔴 Gap 2：前文上下文的“物理截断（500字）”彻底破坏了连贯性与因果链

- **实际现状**：在 [generator.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/generator.ts#L141-L142) 中，`previousChapterSummary` 是通过 `content.slice(-500)`（前一章最后 500 字内容）直接物理截取获得的，且没有回写摘要机制。
- **视角/连贯隐患**：
  - **单视角下**：500 字的截取根本不足以携带上一章全局的关键线索，会导致前文埋下的伏笔被迅速“遗忘”。
  - **视角切换下**：若本章从角色 A 视角切到了角色 B 视角，B 仅仅能看到 A 遭遇的最后 500 字描述，对整章的情报一无所知，导致 B 做出严重脱离因果的突兀行为。
- **改造方案**：
  1. 抛弃 `slice(-500)` 的简单粗暴逻辑。
  2. 每次完成章节后，调用 LLM 生成本章的全局摘要（300 字以内），持久化存储到 Drizzle DB。
  3. 下一章启动写作时，在 [chapter-prompt.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/chapter-prompt.ts) 中，将**已完结章节的滚动结构化摘要链**与**前一章最后段落的笔调**一同传入，兼顾宏观剧情记忆与微观情绪衔接。

#### 🔴 Gap 3：Prompt 模版中缺乏“叙事视角边界与信息屏蔽”的显式约束

- **实际现状**：在 [chapter-prompt.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/chapter-prompt.ts#L26-L38) 中，虽然传入了大纲和人设，但没有对生成的“叙事视角”和“已知/未知信息”进行强指令约束，也未读取配置中的叙事视角属性。
- **视角/人设隐患**：AI 默认倾向于扮演“全能全知者”。不论是第一人称还是第三人称限制视角，都很容易发生“视角越界”，写出视角主角不可能获取的线索或信息，或使主角的性格口吻偏离其人物档案。
- **改造方案**：
  1. 修改 [chapter-prompt.ts](file:///e:/NextCloud/coding/netx.js/story/lib/writer/chapter-prompt.ts)，使其读取小说的叙事视角设定（`perspective`）。
  2. 根据不同视角配置，在 System Prompt 中动态追加差异化的约束：
     - **第一人称/限制视角**：追加限制性指令（如“本章视角主人为【角色名】，只能描述该角色的直接所见所闻所想，严禁越界透露他人隐私或全局未知事件”）。
     - **全知视角**：注入场景平滑过渡指令，防止角色间的视角瞬间撕裂跳转。
  3. 区分 `POV_Character_Profile` 与 `Supporting_Characters_Profiles` 进行传参，强化视角主角的性格本色扮演。
